# Carrier trade search contract

The app engine owns a single opportunity search for the active commander. The carrier package calculates offers using the planner settings, credits, ship capacity, carrier location and installed services captured at submission. The search can also run before the journal identifies a commander if the user supplies the origin and budget.

| Boundary | Contract |
| --- | --- |
| Search | The desktop invokes `/api/carrier/trade` with `action: opportunities`. An optional system is trimmed and limited to 150 Unicode characters. An optional credit budget is a positive finite number up to 10¹⁵. The supported scenario is `profitable`. Boolean `force` bypasses reuse. Only these settings enter the search. |
| Reuse | An identical search can reuse an in-flight request or a result up to ten minutes old when its effective planner inputs still match. The engine starts a new request when the filters or effective inputs differ. |
| Network | The search calls the HTTPS endpoints configured in the carrier and market clients. The desktop cannot supply an endpoint. The network phase has a 95-second budget, and the carrier-route subrequest has a 65-second budget. Individual HTTP calls have a maximum 45-second client timeout and market requests have a 30-second attempt timeout. JSON responses above 16,000,000 bytes are rejected. Redirects are limited to two and must stay on the original HTTPS host and port. |
| Cancellation | A replacement request, relevant planner edit, commander change, journal reset or engine shutdown cancels in-flight network work. The engine checks the operation identity and current planner inputs before publishing progress or results. A late response cannot replace a newer search or publish after shutdown, even if its transport ignored cancellation. |
| UI | The engine returns a detached view of search progress and up to eight normalized offers. Each card contains the fields used to display the market quotes, pickup orders, jumps and costs. The request fingerprint and the planner inputs for applying an offer stay in the engine. The UI uses an opaque generation number to request fresh offers after invalidation. |
| Handoff | The desktop invokes the same command with `action: apply-opportunity` and the selected offer ID. The engine checks that the offer belongs to the current search and that the context and quotes are still fresh, then applies the stored plan atomically with respect to commander changes and shutdown. The search itself has no profile writes. Applying an offer uses the existing planner persistence. |
